# Repository Writing Rules

## Rule 1

One page = one topic.

Never combine unrelated APIs.

Good:

join.md

Bad:

join-split-replace.md

unless they are naturally related.

---

## Rule 2

Every page must follow the same structure.

# Title

## Introduction

## What is it?

## Syntax

## Parameters

## Return Value

## Time Complexity

## Space Complexity

## Basic Example

## Intermediate Example

## DSA Example

## Common Interview Questions

## Common Pitfalls

## Alternatives

## Best Practices

## Key Takeaways

## Related Topics

## Practice Problems

---

## Rule 3

Never explain something twice.

If another page covers it, link to it.

---

## Rule 4

Always include complexity.

Even for built-in methods.

---

## Rule 5

Always include Pythonic solutions first.

Then explain manual implementations when appropriate.

---

## Rule 6

Always explain WHY.

Never only explain HOW.

---

## Rule 7

Prefer readability.

Avoid overly clever one-liners.

---

## Rule 8

Every example should be interview relevant.

Avoid toy examples when a realistic one exists.

---

## Rule 9

Every page must contain at least one "Common Pitfall".

---

## Rule 10

Every page should be readable in 5–10 minutes.

Large topics should be split across multiple pages.

---

## Rule 11

Never leave unexplained magic.

Explain why a method exists.

Explain why interviewers expect it.

---

## Rule 12

All code should use Python 3.12 syntax.

---

## Rule 13

Use Markdown only.

No HTML.

---

## Rule 14

Prefer tables over long paragraphs when comparing APIs.

---

## Rule 15

ASCII diagrams are preferred.

Mermaid diagrams can be added later.
